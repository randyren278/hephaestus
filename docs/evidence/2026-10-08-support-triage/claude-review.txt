## Mutation guard (`checks/mutation_guard.py`, `python/tests/test_mutation_guard.py`)

**Your claims hold:**
- **Mutation deadlines are unchanged.** `--baseline-timeout` only changes `baseline_timeout` (`mutation_guard.py:377`), which only `verify_baseline` uses (`:417`). Each mutation's deadline still comes from `args.timeout` or `mutation_timeout(entry, data, timeout)` (`:382-389`), with the manifest's per-prefix values (`checks.json:17-21`).
- **A green baseline is still required.** `--baseline-timeout` doesn't bypass it; only `--skip-baseline` does. Bad values (0, negative, inf, nan) are rejected before any suite runs (`:378`).
- **Both new manifest mutants should be caught:**
  - `mutation-baseline-deadline-overrides-mutants` (`checks.json:1232`): the test at `test_mutation_guard.py:156` would see run timeouts `[3, 3]` instead of the expected `[3, 0.1]`.
  - `mutation-extended-baseline-skips-green-proof` (`checks.json:1239`): caught by the "baseline: unmutated suite is green" assertion (`:155`), and the test at `:180-205` would error.
- **CI's minimum count still matches.** The `mutation-checks` job requires 5 mutations (`ci.yml:354`), and there are exactly 5 `checks/` entries.

**Risk (not a blocker): the 0.1s mutation deadline in `test_baseline_extension_preserves_the_mutation_deadline` (`test_mutation_guard.py:138`) may be too tight.**
- `_run` sets `PYTHONPYCACHEPREFIX` to a fresh temp directory (`mutation_guard.py:143`). That probably makes the child Python recompile non-frozen stdlib modules like `pathlib` at startup.
- On a slow or loaded runner, the non-hang case could hit the deadline and report TIMEOUT instead of KILLED, so the test fails.
- That matters because CI runs the mutation guard with `--skip-baseline` (`ci.yml:403`). Flaky test failures there can make mutants look killed when they actually survived.
- The fix: keep the same structure (baseline run longer than the mutation deadline) with more margin, e.g. baseline sleep 1.5s, mutation timeout 1s, `--baseline-timeout 5`. The exact call-arguments assertion, which is what catches mutant 1, doesn't depend on timing.

**Minor, fail-closed issues:**
- `--timeout` is still never validated. Without `--baseline-timeout`, a value like `--timeout -1` produces the misleading message "baseline timeout must be positive…".
- A non-numeric manifest `timeout_seconds` now crashes in `math.isfinite` (`:378`) instead of raising a ManifestError. The exit code is still non-zero.
- There's no test combining `--timeout` with `--baseline-timeout`, but the precedence code is simple.
