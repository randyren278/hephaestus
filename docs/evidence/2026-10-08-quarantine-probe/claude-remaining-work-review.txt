## 1. Work that fits the current scope

### A. Quarantined first launch, simulated locally (recommended)

**Untested risk:** Hephaestus's own binaries have no Apple code signing or notarization (`docs/MACOS_INSTALL.md:93`, `docs/RELEASES.md:5`). macOS adds a quarantine flag to browser downloads, and Gatekeeper may block unsigned binaries carrying it. This flag would probably survive installation:
- **Extraction:** the docs tell users to extract with `tar -xzf` (`docs/MACOS_INSTALL.md:27`). macOS tar has historically copied the archive's quarantine flag onto extracted files. That's from general macOS knowledge, not checked here.
- **Installation:** the installer copies the package with `cp -R` (`scripts/package/install.sh:68`). On macOS, `cp` keeps extended attributes unless you pass `-X`.

**Why current evidence doesn't cover it:**
- Acceptance extracts a locally built, unquarantined archive (`scripts/package_macos_acceptance.sh:32`).
- No script or user doc mentions `xattr`, Gatekeeper or `spctl`. Outside dated evidence, the only matches for that search are the two "not implemented" notes above.

So someone directed to the release could hit a first-launch block with no recovery guidance. This is a hypothesis, not a verified defect.

**What to do:** add the quarantine flag to a locally built ARM64 archive, extract it with system tar, install, then run the existing acceptance steps. Launch from a terminal that is *not* listed under Developer Tools; that exemption can hide the result (`docs/MACOS_INSTALL.md:101`). It's reversible, offline and uses no provider.
- **If it passes:** you have evidence that a quarantined archive installs and runs on Apple Silicon.
- **If it fails:** the in-scope fix is documented, honest recovery guidance.

Notarization itself needs an Apple Developer ID, so it belongs to you (section 2). This doesn't replace testing an actual downloaded release.

### B. Codex token usage in comparisons (optional, depends on your call)

Codex reports token counts, and they're saved with the run's evidence (`crates/hephaestus-runtime/src/provider_events.rs:156-176`). However, `input_tokens`/`output_tokens` appear only in that parser and `docs/RUNTIMES.md`. No summary, report or console shows them, and recorded Codex USD is always zero (`:170-172`). Showing tokens per prompt would give Codex comparisons a real usage measure.

It would **not** close the cost requirement as currently written, which needs provider-reported USD or attributable usage evidence (`docs/PRODUCT_READINESS.md:57-63`). It's worth doing only if you'd accept token counts as cost evidence. Otherwise skip it.
