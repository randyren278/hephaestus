# Releases

The release workflow builds macOS archives from a tagged version, checksums them,
adds and verifies Sigstore signatures, records and verifies build provenance,
then publishes a prerelease. Sigstore verifies the
workflow identity; Apple code signing and notarization are not implemented.
The commands to verify a release are below.


`.github/workflows/release.yml` builds and publishes signed macOS release
archives. It runs only on a `v*` tag push, or on manual `workflow_dispatch`
(which rehearses builds, acceptance, inventories and reproducibility without
signing, creating attestations or publishing a GitHub Release, including when
the selected ref is a tag). Signing and publishing require a `push` event on
`refs/tags/v*`, and the tag must match the workspace version.

Each archive is built and accepted on its native architecture: ARM64 on
`macos-15`, Intel on `macos-15-intel`. A wrong host architecture rejects before
building. The installed-package acceptance check must pass before checksumming,
uploading release bytes or signing. Its failure logs use a separate artifact
name and are never merged into published release assets. Ordinary CI also
checks the ARM64 package on pull requests and main.

## Publication and recovery

Before an approved tag push, require main CI to pass for the exact intended
source commit. The tag push starts publication; there is no later owner approval
step in the workflow. Manual dispatch continues to skip signing and publication.

The publisher names the repository explicitly, verifies the remote tag's commit
and uploads into a private draft. It checks the complete asset names, sizes and
SHA-256 digests before publishing as a prerelease without marking it Latest.
The release page includes the capabilities and limits in
[release notes](RELEASE_NOTES.md), followed by generated change notes.

An interrupted upload leaves a private draft. Retrying the original tag-push
run can replace assets only after checking the draft's tag and source marker
against the remote tag's resolved commit. Draft discovery uses all release
listing pages and refuses duplicate tag matches; readbacks pin the release ID.
A completed public release is accepted as an identical retry only when its
source, channel and every asset match; public assets are not overwritten.
Unexpected assets, a different source or failed API inspection refuse recovery.
Workflow concurrency serializes its own runs; operators must not manually
publish or edit the draft while it is uploading. The GitHub API does not provide
an atomic check-and-publish transaction. Preserve failed-run evidence and do not
move the original tag. A source or
workflow correction requires a separately reviewed patch version.

The first prerelease still needs fresh-user quarantined-download and provider
acceptance. Publishing it is not a claim of full product readiness. Changing
it to a full release is a separate owner decision after those checks.

## What a release contains

For each of `arm64` and `x86_64`:

- `hephaestus-v<version>-macos-<arch>.tar.gz` — the relocatable package built
  by `scripts/package_macos.py` (see [docs/MACOS_INSTALL.md](MACOS_INSTALL.md)).
- `hephaestus-v<version>-macos-<arch>.tar.gz.sha256` — its SHA-256 checksum.
- A target-specific CycloneDX 1.5 JSON inventory per bundled Rust binary,
  generated by pinned `cargo-cyclonedx` 0.5.9 in separate jobs that never
  receive the accepted archives. These inventories cover Rust dependencies
  with default features; they do not inventory bundled Node or JavaScript.
- Files ending in .sigstore.json — a Sigstore verification bundle for every archive,
  checksum and Rust inventory, produced by pinned Cosign 3.1.3 using
  the workflow's own GitHub OIDC identity (no long-lived signing key is
  stored anywhere).
- A GitHub build-provenance attestation (via the actions/attest-build-provenance
  Action) attached to each archive and Rust inventory, verifiable with
  `gh attestation verify`. Signing also requires the reproducibility job.

## Verifying a downloaded archive

Use Cosign 3.1.3 for these bundle commands, the same version pinned by the
workflow. Install it and the GitHub CLI from their official distributions.

```sh
# 1. Checksum
shasum -a 256 -c hephaestus-v0.1.0-macos-arm64.tar.gz.sha256

# 2. Sigstore signature (keyless; verifies against the release workflow's
#    own OIDC identity, not a long-lived key)
cosign verify-blob \
  --bundle hephaestus-v0.1.0-macos-arm64.tar.gz.sigstore.json \
  --certificate-identity 'https://github.com/randyren278/hephaestus/.github/workflows/release.yml@refs/tags/v0.1.0' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  hephaestus-v0.1.0-macos-arm64.tar.gz

# 3. GitHub build provenance attestation
gh attestation verify hephaestus-v0.1.0-macos-arm64.tar.gz \
  --repo randyren278/hephaestus \
  --signer-workflow randyren278/hephaestus/.github/workflows/release.yml \
  --source-ref refs/tags/v0.1.0
```

Use the intended version in the filename, certificate identity and source ref.
Do not accept a fork identity, another workflow or a branch rehearsal as an
official release. These checks use the documented
[Cosign identity policy](https://docs.sigstore.dev/cosign/verifying/verify/) and
[GitHub attestation constraints](https://cli.github.com/manual/gh_attestation_verify).
All three should succeed before you run the archive's install.sh (see
[docs/MACOS_INSTALL.md](MACOS_INSTALL.md)).

## Reproducibility: what is actually proven

The `reproducibility` job in `.github/workflows/release.yml` checks out the selected commit once,
builds the `arm64` archive twice from that single checkout with the same
toolchain, and fails the workflow if the two archives are not byte-identical.
Locally, the same experiment (two `cargo build --release` runs of the `hephaestus`
binary from clean, separate target directories) produced identical SHA-256
hashes, and the packaging script's tar/gzip output is explicitly normalized
(sorted entries, zeroed mtimes/uid/gid, empty gzip filename/mtime header) so
that two archives built from the same staged files are byte-identical
regardless of when or in what order they were written.

Read that claim narrowly. It proves the packaging pipeline is deterministic
**on one machine, from one checkout, with one toolchain install** — it does
not prove independent reproducibility across different builders, operating
system patch levels, or Rust versions, because no second, differently
provisioned builder exists yet. A true SLSA-style independent-rebuild proof
(a second party rebuilding from the tag and confirming the same hash without
trusting this workflow) is not set up. This is recorded as tech debt, not
claimed as done.

## What is not covered

- No Linux or Windows release archives exist; only macOS `arm64`/`x86_64`
  (see [docs/MACOS_INSTALL.md](MACOS_INSTALL.md) for the existing platform
  limits).
- The release workflow does not publish to Homebrew, crates.io, or any other
  package index.
- The [manual release rehearsal](evidence/2026-10-08-native-release-rehearsal/README.md)
  passed native ARM64 and Intel package acceptance, both Rust inventories and
  same-machine reproducibility at `739cb9c`. Signing, attestation and publication
  were skipped for that dispatch; their actual hosted acceptance remains open.
- Cosign keyless signing depends on GitHub's OIDC token issuer and Sigstore's
  public Fulcio/Rekor infrastructure being reachable from the runner; a
  transient outage there fails the `sign-and-attest` job rather than
  silently skipping signing.
